# Agent 机构审核 CLI 需求

## 1. 背景

批量导师投稿的主要审核成本不是逐项核验导师姓名、邮箱、职称或个人主页内容，而是把投稿中的学校、学院、研究院、系所、中心和实验室字段规范化，并安全地映射或写入机构树。

现有审核页面能够生成结构化审核评论，但浏览器交互不适合 Agent：信息密度低、批量筛选困难、状态不能方便地跨会话复用，而且网页中的交互状态不能直接作为可信后端输入。仓库已有的 Python 后端已经负责审核评论、机构树、来源域名、提案集合和最终落库校验，因此新增能力应建立在现有可信逻辑上，而不是复制一套审核规则。

## 2. 目标

提供面向 Agent 的自描述 CLI 和配套 Skill，使 Agent 能够：

1. 一次只处理一个批量投稿 PR；
2. 用低 Token 输出精确读取所需信息；
3. 自动完成确定性强的机构规范化决定；
4. 把剩余歧义压缩为少量、明确、可回答的问题；
5. 保存与 PR 版本绑定的本地审核底稿；
6. 根据用户回答补齐决定并在本地完整预演；
7. 仅在用户明确授权后发布一次正式审核评论；
8. 跟踪现有可信队列的落库、合并和发布状态。

## 3. 非目标

- 默认不访问导师个人主页核验投稿信息是否真实。
- 默认不核查姓名、邮箱、职称、研究方向或论文内容。
- 不使用浏览器完成审核。
- 不让 Agent 自主裁决模糊的机构层级、合署关系或多机构混写。
- 不绕过现有 GitHub Actions、审核评论 Schema 或串行落库队列。
- 不让 CLI 直接修改正式数据、将 PR 标记 Ready 或合并 PR。
- 不把完整 CLI 手册复制进 Skill。

来源 URL 仍必须通过现有的最终机构批准域名校验。这是入库结构约束，不代表需要访问页面检查其内容。

## 4. 人机协作模型

### 4.1 Agent 可自动处理

只自动处理能够由清单、机构注册表或既有审核历史确定的决定：

- 同一父级下正式名称或别名的唯一精确匹配；
- 已记录的历史路径纠正；
- 空的可选下级字段；
- 系所字段与学院完全同名，归入学院；
- 系所字段与学校完全同名，归入学校；
- 名称和父级都唯一明确的新机构创建；
- 明确的机构类型后缀，例如学院、研究院、系、中心和实验室；
- 来源域名与最终机构继承域名兼容；
- 多个分组对同一个确定机构的复用。

自动决定必须可解释、可复现，并记录规则代码、简短理由和置信来源。

### 4.2 必须交给用户决定

- 系所字段看起来是学院或研究院，但同级或下级关系不明确；
- 研究院在该校的实际层级不能从现有树或历史裁决确定；
- 括号、斜杠或并列名称可能表示别名、合署机构或多个独立机构；
- 一个字段混合多个机构；
- 多个现有机构均可匹配；
- 是否保存可能改变语义的永久别名；
- 是否保存新的路径纠正规则；
- 个别导师是否应脱离整组映射到另一机构；
- 已有导师资料冲突、任职冲突或其他非纯机构规范化问题。

每个问题必须包含稳定问题 ID、最小必要上下文、建议选项、建议理由以及 CLI 可接受的选择值。不能把整份清单或大段 JSON直接交给用户。

### 4.3 正式提交

发布带 `mentor-data-organization-review` 标记的 PR 评论即视为最终批准。正式提交必须满足：

- 所有问题已解决；
- PR 仍开放且属于仓库内部批量分支；
- PR head SHA 与底稿绑定值一致；
- 审核清单 SHA-256 与底稿绑定值一致；
- 在最新 `main` 上完成临时 worktree 预演；
- 现有 Schema、机构树、来源域名和提案集合校验全部通过；
- 用户在当前任务中明确授权提交；
- 命令提供与目标 PR 一致的显式确认参数。

CLI 只发布审核评论，后续由现有可信队列应用决定、更新分支、标记 Ready、Squash 合并和发布。

## 5. Agent 友好的 CLI 契约

### 5.1 自描述

- 支持通过 `uv tool install --editable .` 一次安装到用户 PATH；从其他工作区调用时，自动定位 editable 源码仓库，也允许 `MENTOR_DATA_ROOT` 或 `--root` 显式覆盖。
- `mentor-data review doctor` 只读检查 CLI、可信仓库、GitHub CLI 和 Codex Skill，仓库内 Skill 即视为可用，不要求全局安装；返回紧凑的机器可读状态与待办动作。
- `mentor-data review --help` 描述完整工作流和安全边界。
- 每个子命令提供用途、前置条件、默认输出、筛选参数和下一步示例。
- 错误输出包含稳定错误代码、简短原因和可执行的下一步命令。
- Skill 只需让 Agent先读取 CLI 帮助，不维护易过期的参数清单。

### 5.2 渐进披露和低 Token 输出

- 默认输出紧凑 JSON；人类可读输出必须显式选择。
- 队列只输出 PR 编号、标题、状态和审核规模。
- 分组列表默认不输出导师行详情。
- 问题列表只输出问题 ID、路径、问题类型、建议选择和选项值。
- 单项详情通过稳定 ID 显式读取。
- 支持按状态、问题类型、规则、机构层级和文本查询筛选。
- 支持 `--fields` 精确选择输出字段；未知字段必须报错。
- 所有列表输出包含 `count`，并具有稳定排序。
- 不输出令牌、完整 GitHub 事件、无关 PR 字段或完整机构注册表。

### 5.3 工作底稿

底稿默认保存在被 Git 忽略的 `.work/agent-reviews/pr-N.json`，并至少记录：

- Schema 版本；
- 仓库名、PR 编号、Issue 编号；
- PR head SHA、base SHA、清单 SHA-256 和注册表 SHA-256；
- 自动决定及其规则和理由；
- 待用户决定的问题；
- 用户回答；
- 生成的完整审核决定；
- 最近一次预演结果和时间；
- 正式提交的评论 ID（如有）。

底稿发生版本漂移时不得静默复用旧答案。只读命令可以报告 `stale`，修改、预演和提交命令必须拒绝继续并提示重新规划。

### 5.4 建议命令能力

- `review queue`：列出开放的批量审核 PR，支持状态和文本筛选。
- `review doctor`：从任意工作区诊断本地安装、仓库定位和 Skill 可发现性。
- `review inspect --pr N`：读取或刷新目标 PR 清单，返回极简摘要。
- `review plan --pr N`：运行确定性规则并创建或刷新底稿。
- `review groups --pr N`：筛选并列出机构路径分组。
- `review group --pr N --id ID`：读取一个分组的必要详情。
- `review questions --pr N`：筛选并列出待决定问题。
- `review question --pr N --id ID`：读取单个问题及完整选项。
- `review answer --pr N --id ID --choice VALUE`：记录用户决定及必要参数。
- `review check --pr N`：在最新 `main` 上完整预演并输出影响摘要。
- `review decision --pr N`：按需输出完整决定或正式评论正文。
- `review submit --pr N --confirm-pr N`：再次预演后发布正式评论。
- `review status --pr N`：报告评论、Actions、PR 和 Issue 状态。

最终命令名称可以遵循现有 CLI 风格调整，但必须覆盖上述能力和安全边界。

## 6. 确定性规则约束

- 规则必须是纯函数或接近纯函数，并有独立单元测试。
- 自动规则只能使用 PR 清单、注册表和仓库内既有审核记录。
- 不得以模糊名称相似度作为自动合并机构的唯一依据。
- 不得根据名称后缀自动决定有歧义的父级关系。
- 新学校缺少官网和批准域名时必须提问。
- 新学院以下机构可以继承上级批准域名，但最终来源仍须兼容。
- 记录冲突和身份冲突永不由普通机构规则自动接受。
- 每条自动决定必须可在摘要中追溯到规则代码。

## 7. 输出与错误规范

成功输出统一包含：

```json
{"ok":true,"command":"review.plan","data":{}}
```

失败输出写入标准错误并包含：

```json
{
  "ok": false,
  "error": {
    "code": "review_questions_pending",
    "message": "还有 2 个问题未解决",
    "next": "mentor-data review questions --pr 81 --status pending"
  }
}
```

CLI 退出码：成功为 `0`，业务或输入错误为 `2`，外部暂时性失败为非零且不得修改底稿或远程状态。

## 8. 验收标准

- Agent 无需浏览器即可完成从读取 PR 到生成审核评论的全流程。
- 默认路径不发起导师主页内容请求。
- 可用一条命令查看队列和单个 PR 的低 Token 摘要。
- 可仅列出待用户回答的问题并逐项读取、回答。
- 确定项自动完成，歧义项不会被静默决定。
- 旧 PR SHA 或旧清单上的底稿不能提交。
- 有未回答问题时不能预演为可提交，也不能提交。
- `submit` 未提供匹配的显式确认参数时不会产生远程写入。
- 预演复用现有可信 Python 业务逻辑，并在最新 `main` 上运行。
- CLI 和规则有覆盖成功、歧义、漂移、冲突和提交保护的自动化测试。
- Skill 简洁、通过官方 Skill 校验，并把命令细节留给 CLI 自描述帮助。
