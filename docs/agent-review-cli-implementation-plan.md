# Agent 机构审核 CLI 实现计划

## 1. 实现原则

- 复用现有 `organization_review`、`internal_pulls`、`promotion` 和仓库校验逻辑。
- 把 GitHub 读取、规划、底稿、预演和提交分层，便于测试时注入假数据。
- 默认只读；远程写入集中在单一提交入口。
- 先实现精确、保守的规则，再扩展覆盖率，不以自动化比例牺牲机构树正确性。
- CLI 输出稳定、紧凑并支持渐进披露。
- 每完成一个阶段都运行定向测试、审查差异并修复后再继续。

## 2. 阶段一：文档与现有链路基线

交付：

- `docs/agent-review-cli-requirements.md`
- 本实现计划
- 现有审核 Schema、网页决策编码、可信评论和落库队列的复用点清单

审查：

- 确认需求没有把导师内容真实性核验带回默认流程。
- 确认正式评论仍是唯一远程审核写操作。
- 确认本地底稿位于 `.work/`，不会进入 Git。

## 3. 阶段二：核心领域模型与 GitHub 只读入口

新增模块建议：

- `mentor_data/agent_review.py`：底稿、摘要、规则、问题和决定构建。
- `mentor_data/agent_review_github.py`：GitHub CLI/API 读取与唯一提交接口。
- `mentor_data/agent_review_cli.py`：参数、筛选、字段投影和紧凑输出。

实现：

1. 定义稳定的底稿 Schema 版本和数据类。
2. 读取并校验开放内部批量 PR。
3. 按 PR head SHA 读取审核清单和提案文件。
4. 计算清单摘要并写入原子底稿。
5. 实现统一 JSON envelope、`--fields`、`--format` 和错误代码。
6. 实现 `queue`、`inspect`、`groups`、`group`。

测试与审查：

- 使用假 GitHub runner 覆盖分页、无效 PR、超限内容和无关字段抑制。
- 对默认输出做精确快照或字典断言，防止意外输出完整清单。
- 运行 Ruff 和新增测试，审查网络与文件路径边界。

## 4. 阶段三：确定性规划和人机问题

实现：

1. 从机构注册表建立父级约束的精确名称索引。
2. 复用清单中的 `suggested_organization_id` 和历史路径纠正。
3. 实现保守自动规则：唯一精确匹配、空层级、重复父级、明确的新机构节点。
4. 为歧义路径、混合机构、别名、记录冲突和身份冲突生成稳定问题。
5. 实现 `plan`、`questions`、`question`、`answer`。
6. 支持问题状态、类型、规则、层级和文本筛选，以及字段投影。
7. 从底稿构建完整的 `organization-review-decision`。

问题 ID 和自动决定 ID 必须由 PR、分组、问题类型和目标层级稳定派生，重新规划同一版本不得改变。

测试与审查：

- 覆盖现有测试夹具中的学院误填系所、同名父级、同级学院、研究院、混合机构和历史纠正。
- 验证模糊名称不会自动映射。
- 验证冲突行始终产生问题或保守拒绝建议，而不是自动接受。
- 审查每条自动规则是否能给出短理由和可复现证据。

## 5. 阶段四：本地预演、决定输出与安全提交

实现：

1. 获取最新 `origin/main` 和 PR head，不切换用户工作树。
2. 在临时 worktree 中物化 PR 的受限提案文件。
3. 构造本地受信任审核评论对象，调用现有 `apply_organization_review()`。
4. 调用现有提案集合和仓库校验，生成影响摘要。
5. 实现 `check` 和 `decision`。
6. 实现 `submit`：重新读取远程版本、再次预演、检查 `--confirm-pr`，最后调用 GitHub API 发布唯一正式评论。
7. 实现 `status`，读取正式评论、PR 标签、Draft/merged 状态和来源 Issue 状态。

测试与审查：

- 预演测试必须使用真实临时 Git 仓库和现有业务函数。
- 验证未回答问题、版本漂移、预演失败和确认号不匹配均不会调用远程写入。
- 验证提交入口只有一个创建评论的 API 调用。
- 验证评论长度、marker 和紧凑编码与后端一致。

## 6. 阶段五：Skill

在仓库内创建：

```text
.agents/skills/review-mentor-data-pr/
├── SKILL.md
└── agents/openai.yaml
```

Skill 只描述协作原则：

- 默认相信导师投稿，不调查个人主页内容；
- 一次只处理一个 PR；
- 使用 CLI 自描述帮助；
- 先规划确定项，再把歧义交给用户；
- 不替用户裁决不确定机构关系；
- 未经明确授权不得提交；
- 提交后跟踪到明确终态。

使用 `skill-creator` 的初始化和验证脚本生成、校验元数据。Skill 不包含重复脚本或完整 CLI 参数表。

## 7. 阶段六：整体验证与交付

按风险递增运行：

1. 新增 Agent 审核单元测试；
2. 现有机构审核、晋升队列和 CLI 测试；
3. JavaScript 审核逻辑测试，确认评论编码兼容；
4. `uv run mentor-data validate`；
5. `uv run ruff check .`；
6. `uv run pytest`；
7. Skill `quick_validate.py`；
8. 对一个开放 PR 运行只读 `inspect` 和 `plan` 烟雾测试，但不运行 `submit`。

最终审查：

- 检查 Git diff、未跟踪文件、秘密和临时数据。
- 检查需求和实现计划中的验收项。
- 更新相关维护文档中的 CLI 入口。
- 创建聚焦提交并推送 `codex/` 分支。

## 8. 完成定义

- 需求文档和实现计划已提交。
- CLI 覆盖查询、规划、提问、回答、预演、决定输出、提交保护和状态跟踪。
- 默认工作流不核验导师个人资料内容，也不需要浏览器。
- 所有远程写入均受显式授权和二次预演保护。
- Skill 可被自动发现并通过校验。
- 全部仓库测试和静态检查通过。
- 变更已提交并推送远程分支。
