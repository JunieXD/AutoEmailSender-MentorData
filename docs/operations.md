# 远程仓库启用与日常维护

## 一次性启用

1. 在个人账号下创建公开仓库 `AutoEmailSender-MentorData`，默认分支为 `main`。
2. 推送本仓库；在 Actions 设置中允许 GitHub Actions 读写仓库并创建 Pull Request。
3. Pages 的构建来源选择 GitHub Actions。新队列会直接完成受校验的 Squash 合并，不依赖仓库 Auto-merge 开关。
4. 运行一次 `Bootstrap repository labels`，创建投稿、审核和 `status:needs-attention` 标签。
5. 给 `main` 禁止强推和删除。内部投稿 PR 不依赖贡献者分支上的代码，可信队列会在合并前重新完成全部校验。
6. 启用私密漏洞报告，并确认 Issue Forms 可用。

自动化只使用仓库短期 `GITHUB_TOKEN`，不保存个人 PAT。

## 完整处理链路

单条投稿、批量投稿和错误反馈都遵循同一套原则：一个 Issue、一个固定分支、一个 PR。

- 单条投稿：`submission/issue-N`
- 批量投稿：`batch/issue-N`
- 错误反馈：`report/issue-N`

Issue 工作流只解析输入并创建提案 PR，不直接修改正式数据。重复运行时会识别已有 PR 或已完成收据，不会再创建第二条分支或第二个 PR。PR 标题与 Issue 标题完全相同。

`Promote ready mentor data Pull Requests` 是唯一的正式落库队列。它会按 PR 编号依次处理，始终在最新 `main` 上重新载入提案、应用审核结果、校验整个仓库、写入 `reviews/promotions/` 收据，再更新原 PR 并 Squash 合并。多个投稿同时到达时不会互相覆盖；`main` 在处理期间变化时，本次会停止并由下一轮从新版本继续。

队列会在投稿准备成功、维护者完成审核、PR 更新、定时恢复或手动运行时启动。某条 PR 的数据确实需要人工处理时，才会增加 `status:needs-attention` 并保留一条可更新的说明；它不会阻塞后面的投稿。修正后移除该标签即可重试，也可以手动运行队列并启用 `include_attention`。

正式数据合并后，Pages 只部署当前 v2 发布和它引用的内容对象。数据没有变化时不会产生新的版本或 `gh-pages` 提交；学院内容没有变化时会复用原对象。发布成功后，来源 Issue 才会自动关闭。每小时的恢复任务会补处理因临时故障遗漏的发布或 Issue 关闭。

## 维护者如何审核

### 单条投稿

自动资格投稿会直接进入落库队列。需要人工审核时：

1. 在 Draft PR 中核对并按需修改 `accepted`、`target_mentor_id` 和机构映射；
2. 确认来源证据和最终值；
3. 将 Draft 标记为 Ready。之后无需手动合并。

### 批量投稿与新机构

批量投稿可以包含多个学校和学院，系统会按投稿中的学校、学院、系所组合分组。Issue 的唯一状态评论会提供审核页面链接。

在审核页面中：

1. 对每个组合选择现有机构、新建机构或归到已确认的上级；
2. 修改正式名称，决定是否把投稿简称保存为别名；
3. 把个别导师调整到其他现有或本次新建的机构，或拒绝该行；
4. 对“疑似同一导师，学院不一致”的行，核对并选择“新增双聘任职”或“已调动到新学院”；调动时必须选择结束哪条当前任职，两种情形都必须填写官网依据；
5. 复制结构化审核结果并粘贴到对应 PR。

双聘默认保留原主任职；审核者可以明确把新任职设为主任职。调动会将选择的原任职标记为历史任职，并把新学院设为主任职。若最终机构已经是该导师的当前任职，页面会提示无需新增任职，后端也会拒绝重复的双聘/调动决策。

如果选择“新建机构”，但正式名称已经与同一父级下的现有正式名或别名完全匹配，页面会自动切换为现有机构，可信后端也会再次执行同样的复用规则。不同学校下的同名学院不会被误合并。

只有新学校必须有独立官网。学院、系所、办公室或实验室没有独立页面时可以留空并继承上级批准域名。高校官网允许 HTTP 或 HTTPS。

机构审核评论必须由当前仍有写入权限的 `OWNER`、`MEMBER` 或 `COLLABORATOR` 发布。队列会从默认分支运行可信代码，重新校验评论、清单摘要、PR 来源、机构层级、官网和批准域名；提案分支中的程序不会执行。

### 错误反馈

错误反馈始终人工审核。在 Draft PR 中填写最终 `decision` 和 `moderator_reason`；接受或部分接受时填写 `accepted`。将 Draft 标记为 Ready 后，队列会自动落库、合并和发布。被拒绝的真实审核结论同样会留下 Resolution 和发布收据。

## 通知邮件的边界

工作流已经避免正常步骤中的重复评论：每个来源 Issue 只有一条可更新的状态评论，PR 只在需要人工修复时新增一条状态说明，无变化的 Pages 构建也不会推送提交。

GitHub 自己生成的 `pushed commits`、`merged` 和 `closed` 动态不能由 Actions 关闭。若不想收到这些邮件，需要在仓库页面把 Watch 改为 `Custom`，只订阅需要的 Issue 类别，或在 GitHub 通知设置中关闭邮件投递；工作流没有权限替用户修改个人通知设置。保留 Issue 自动关闭就必然会产生一次 GitHub 的关闭事件。

## 封禁与撤销

运行 `Revoke contributor data`，先保持 `apply=false` 查看影响范围，再以数字 GitHub 用户 ID、原因代码和所需封禁范围重新运行并创建 Draft PR。确认独立来源仍然成立、唯一来源导师已撤下后合并。

内部封禁名单能阻止该数字 ID 的新投稿或反馈进入数据集。若还要阻止其继续在个人仓库创建 Issue，需要仓库所有者另外使用 GitHub 的账号屏蔽功能；仓库 `GITHUB_TOKEN` 不能代替账户级屏蔽。
