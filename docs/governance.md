# 审核与治理

## 审核队列

所有投稿先经过只读校验。Actions 输出规范候选文件和决策摘要：

- `auto_eligible`：无冲突且满足全部自动策略。
- `manual_review`：年轻账号、新机构、未知别名、字段冲突、多个主邮箱/任职等。
- `rejected`：封禁用户、非法结构、危险文件或缺少必要字段。

自动资格投稿仍通过固定内部分支和 PR 留下审计记录。人工投稿生成 Draft PR，维护者修改审核后值或提交机构审核结果后，由可信串行队列自动完成落库和合并。批量文件中的普通坏行单独记录，其他安全有效行继续进入审核；危险文件结构仍整包拒绝。

## 机构注册

普通贡献者只能建议机构名称。以下变更必须由仓库维护者或专门授权的机构维护者确认：

- 创建新机构；
- 新增可能改变语义的别名；
- 机构改名、合并、关闭或拆分；
- 修改机构上级关系；
- 添加新的官方域名。

已登记的正式名称和完全匹配别名可自动归一化。

维护者即使选择“新建机构”，只要填写的正式名称与同一父级下已有机构的正式名或别名完全匹配，页面和可信后端都会自动复用现有机构。匹配始终受父级约束，不会把不同学校下的同名学院合并。

批量机构审核按投稿者填写的学校、学院、系所组合聚合，不限制一次投稿涉及的学校数量。维护者可以对组合执行现有机构映射、新建机构、归到上级或整组拒绝，也可以逐行拆分到其他现有机构或拒绝个别行。保存别名是显式选择；不保存时只修改本次提案的 `accepted.organization_id`。原始 `submitted_*`、GitHub 投稿者和 Issue 来源始终保留。

每次已应用的决策写入 `reviews/resolutions/`，记录清单摘要、审核评论、审核者数字 ID、创建或更新的机构，以及映射、拒绝和普通无效行。清单发生变化后，旧评论会因摘要不一致而失效；机构注册表在排队期间变化时，队列会在最新注册表上重新检查名称、层级和域名。

## 错误反馈

错误反馈永不自动修改数据。维护者可以接受全部、接受部分、要求证据、拒绝或标记重复。

审核 PR 中的 `accepted` 是机器校验的结构化补丁。需要修改邮箱、双聘、学院或主页时，维护者复制 `before` 中对应完整数组并编辑最终状态；系统会规范化邮箱、核对机构和官方域名，并把 Resolution 追加为变更来源。退休、离职、去世或移除会关闭所有当前邮箱、主页和任职，并从默认导入分片撤下。

一次错误反馈不代表恶意。只有明确伪造证据、反复骚扰或持续绕过规则时才封禁。错误反馈者的既有有效导师贡献不会仅因一次无效反馈而自动撤销。

## 封禁与撤销

封禁名单以 GitHub 数字用户 ID 为准。封禁可以分别作用于 `contribute` 和 `report`，也可以同时作用于两者。

撤销某用户时：

1. 将其全部有效 Claim 标记为 `revoked` 或移出有效声明集；
2. 从规范实体的字段来源中移除这些 Claim；
3. 用剩余独立 Claim 重建规范值；
4. 无任何来源的字段清空或进入争议状态；
5. 无任何有效来源的导师标记 `removed`；
6. 发布 `revocations.json`，但不远程删除用户本地数据。

撤销还会清理该用户仍在主分支等待处理的投稿，以及指向已删除导师的待审核反馈。历史 Resolution 和 Git 历史可以保留，当前可导入数据不再包含被撤销的唯一来源。

## 可信维护者

个人仓库阶段由仓库所有者负责最终审核。规模扩大后可授予可信维护者有限职责，例如只审核某所学校。账号年龄不等于可信维护者身份。
